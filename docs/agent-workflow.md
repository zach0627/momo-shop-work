# Human ↔ Agent 協作紀錄

這個專案由一位工程師（Human）與 Claude Code（Agent）協作完成。這份文件記錄**怎麼分工、Human 在哪裡糾正了 Agent、Agent 在哪裡出錯、以及從中得到的做法**。它與 git history 一起，是「AI / Agent Supervision」的第一手紀錄。

逐步計畫與完成紀錄在 [`MoMO面試/Phase 2 — Implementation.md`](./MoMO面試/Phase%202%20—%20Implementation.md)。

## 1. 工作協議

先設計、後實作；設計文件是 source of truth。

每一個實作步驟固定走這個迴圈，Agent 不跳步、不偷做下一步：

1. **實作** — 有邏輯的部分先寫測試 → 確認紅燈，且是因為**正確的理由**紅 → 最小實作 → 綠燈。
2. **驗證** — 跑該步的驗證指令（驗證關卡不使用快取），貼出實際輸出。失敗照實說。
3. **回報** — 變更清單、驗證結果、有沒有偏離設計以及原因。
4. **Review** — Human 看過才 commit。
5. **Commit** — Conventional Commits，帶 `Co-Authored-By`。每個 commit 後 `main` 都是綠的。

分工原則：**決定權在 Human 的事，Agent 提出建議與理由後停下來等**（架構取捨、要不要公開某個檔案、專案放在哪個磁碟）；**可逆、且在已同意範圍內的事，Agent 直接做並回報**。

## 3. Agent 的自我審查（設計 v1 → v2）

Human 要求 Agent 在定案前重新審查自己的設計。Agent 找到 8 個問題，其中影響最大的三個：

1. `ProductCard` 沒講清楚吃什麼型別 → 直接吃 `Product` 就會變成 `ui → data-access`，違反自己訂的分層。改為 ui 宣告最小形狀、靠 structural typing 傳入。
2. hooks 直接 import repository singleton → 「只換一個實作檔」其實做不到，測試也只能吃 55 筆真 fixture。改為 Context 注入。
3. 交付順序是水平分層（util → ui → data → …）→ 時間用完時可能連詳情頁都還沒出現。改為 walking skeleton 先行，不可砍的先做。

完整 8 點見[設計筆記](./MoMO面試/Phase%201%20—%20%20Design%20and%20Planning.md)開頭。

## 6. 環境備註

開發機是 2018 年的筆電（i7-8750H、16 GB RAM），專案位於 5400 轉的傳統硬碟，防毒即時掃描開啟。每個 Nx / Vitest 指令都很慢 —— 實測一個 0.5 秒的測試總耗時 34 秒（import 16 秒 + jsdom 環境 16 秒）。**與程式碼無關。**

**診斷被修正過一次，值得記下來。** Agent 起初把原因歸給傳統硬碟，並預期搬到 SSD 會快 5–10 倍。在 SSD 上建立測試複本後實測：安裝依賴確實快很多（50 秒 vs 3 分鐘），但跑測試沒有明顯變快。再量才發現 CPU 負載 100%、可用記憶體只剩 1.5 GB —— **真正的瓶頸是 CPU 與記憶體**（每個 Vitest 行程都要起一個 jsdom，Nx 預設同時跑 3 個 task，再加上 daemon 與 plugin worker），硬碟只是讓它更糟。教訓：先量再下結論；第一個看起來合理的原因不一定是主因。

決定：專案維持在原磁碟（基準）。另有一份放在 SSD 的測試複本，**只用來跑安裝與測試**：單向同步（基準 → 複本）、複本沒有 `.git` 所以無法從那裡 commit。它同時是一個沒有 `node_modules` 的乾淨環境，第一次使用就抓到 lockfile 過期的假綠燈（見 §4）。

因應方式：

```bash
NX_DAEMON=false NX_ISOLATE_PLUGINS=false pnpm nx run-many -t lint test typecheck --parallel=1
```

- `NX_ISOLATE_PLUGINS=false`：否則 plugin worker 子行程無法在 30 秒內連線而載入失敗。
- `--parallel=1`：否則 Vitest worker 啟動逾時，而且同時跑多個 jsdom 會把 CPU 與記憶體吃滿。
- 日常開發使用 Nx 快取；只有驗證關卡才加 `--skip-nx-cache`。
- 失敗的 Nx 指令會留下孤兒 node 行程（曾發現 7 個掛了 23–55 分鐘），它們會持續佔用資源讓後續指令更慢。指令異常結束後要檢查並清掉。

在資源充足的機器上不需要這些參數。
